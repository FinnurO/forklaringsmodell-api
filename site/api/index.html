API

Et REST-API i .NET 10 som lar en saksbehandlingsløsning registrere fakta, vurderinger og vedtak, og lese ut en frosset, hydrert forklaring av hvorfor et vedtak ble som det ble. Her er det du trenger for å kjøre det og bruke det.

1

Kom i gang

Alt du trenger er .NET 10 SDK. Databasen er en lokal SQLite-fil som opprettes og fylles med eksempeldata første gang du starter API-et.

Fra rotmappen i repoet:

dotnet build
dotnet test
dotnet run --project src/Forklaringsmodell.Api
  • Forutsetning: .NET 10 SDK. Alle fire prosjektene i løsningen bygger mot net10.0.
  • Databasen migreres og seedes automatisk ved oppstart når miljøet er Development. Seed-dataen kjøres bare hvis databasen er tom, og gir et komplett dagpenger-eksempel (sak, faktum, vurderinger med alle utfallstyper, vedtak med virkning) pluss en oppfølgende sak med saksrelasjon og kryss-sak-referanser. SQLite-filen heter forklaringsmodell.db; slett den for å starte på nytt.
  • Swagger UI er slått på i Development og gir en utprøvbar oversikt over alle endepunkter: http://localhost:5013/swagger. Startprofilen https åpner i tillegg https://localhost:7151/swagger.
  • Utforsker: API-et serverer også en enkel utforskningsside fra wwwroot/index.html på rotadressen.

Vil du bruke HTTPS-porten, velg profilen eksplisitt:

dotnet run --project src/Forklaringsmodell.Api --launch-profile https

Utenfor utvikling

Swagger, automatisk migrering og seeding er bare aktive i Development. I andre miljøer må databasen settes opp separat.

2

Konvensjoner

Noen få regler gjelder for hele API-et.

Format

  • JSON med camelCase i både forespørsel og svar (sakId, utlosendeHendelse, forelderVurderingId). Norske tegn er skrevet om i feltnavn: spraakKode, belop, erLaast.
  • Enumer er strenger ("GenerativKI", "IkkeOppfylt"), ikke tall.
  • Id-er er GUID-er og genereres av serveren. Du oppgir aldri en id når du oppretter en rad, bare når du refererer til en annen.
  • Tidspunkter er ISO 8601 med tidssone (2026-10-01T09:30:00Z). Utelater du innhentetTidspunkt på faktum eller tidspunkt på partsmedvirkning, settes «nå».
  • Flerspråklige felt er lister med én variant per språk: 
    [
  { "spraakKode": "nb", "verdi": "Tillatelse til rehabilitering av skorstein" },
  { "spraakKode": "nn", "verdi": "Løyve til rehabilitering av skorstein" }
]
    Gjelder hovedhensyn, forkastedeUtfall (vurdering), beskrivelse, lopendeVilkar (virkning) og standardTekst (vilkår). spraakKode er fri tekst, men samme språk kan ikke forekomme to ganger i samme felt, og både spraakKode og verdi må være utfylt.

Append-only

Det finnes ingen PUT eller DELETE på vedtak, forklaringslogg, virkninger, faktum, vurderinger eller referansedata. Det eneste PUT-endepunktet i hele API-et er /api/saker/{id}, og det endrer bare tittel og status på selve saksmappen. Korrigeringer gjøres ved å opprette nye rader, for eksempel POST /api/faktum/{id}/transformer, som lager et nytt subsumert faktum som peker tilbake til det opprinnelige via avledetFraFaktumId.

Når et vedtak opprettes, fryses alt det refererer til. I svarene vises det som erLaast: true på faktum, vurderinger, kilder, regler og vilkår. Referanser på tvers av saker (faktumIder eller refererteVurderingIder som tilhører en annen sak) kreves å peke på rader som allerede er frosset der.

Statuskoder og feil

Statuskoder API-et bruker
KodeNår

201 CreatedVellykket POST som oppretter en rad. Svaret er den opprettede raden.

Påkrevde og valgfrie enumfelt

De fleste enumfeltene i forespørslene er vanlige, ikke-nullable felt. Utelater du dem, får de enumens første verdi som standard (for eksempel type: "Raatt" på faktum eller fastsettelsesmate: "Statisk" på en virkning). Tre felt er derimot gjort nullable i forespørsels-DTO-en nettopp for at valideringen skal kunne kreve dem. Uten dette ville standardverdien alltid sett «utfylt» ut:

  • utlosendeHendelse på POST /api/saker.
  • utfall på POST /api/saker/{sakId}/vurderinger. En vurdering skal finnes selv når vilkåret ikke ble vurdert, og utfallet skiller det fra en reell konklusjon.
  • grunnlagstype på POST /api/vilkar.

Mangler ett av dem, får du 400 med «… er obligatorisk». Øvrige valideringsregler:

Typisk flyt

Fra tom database til en lesbar forklaring i sju steg. Eksemplene er kortet ned til det vesentlige og bygget på piperehabiliterings-eksempelet. Verdier i <vinkelparenteser> er id-er du har fått i svaret fra et tidligere steg.

1. Opprett referansedata

Rettskilder først, siden kilder, regler og vilkår skal peke på dem. Hvert POST-svar inneholder id-en (rettskildeId, kildeId, regelId, vilkarId) du trenger videre.

2. Opprett sak

POST /api/saker 
{
  "tittel": "Søknad om rehabilitering av skorstein – Eiganesveien 12",
  "status": "UnderBehandling",
  "utlosendeHendelse": "Soknad"
}

Svaret (201) har sakId, opprettet og sistEndret. Videre bruker du sakId i stiene.

3. Registrer faktum

POST /api/saker/{sakId}/faktum 
{
  "kildeId": "<kildeId>",
  "type": "Raatt",
  "struktur": "Strukturert",
  "verdi": "Tiltaket er innvendig fôring av eksisterende skorstein, uten endring av utvendige dimensjoner."
}

Må et faktum korrigeres eller tolkes, kaller du POST /api/faktum/{id}/transformer med en ny verdi. Originalen blir stående.

4. Registrer vurderinger

Start med rotvurderingen (hovedvilkåret), og registrer deretter delvurderingene med forelderVurderingId som peker på den. Foreldrevurderingen må tilhøre samme sak. Alle vurderingene kan peke på samme vilkarId, og utfall er påkrevd, også for vilkår som ikke ble vurdert (Uaktuelt, IkkeVurdert, Uavklart).

POST /api/saker/{sakId}/vurderinger – rot 
{
  "regelId": "<regelId>",
  "type": "Deterministisk",
  "utfall": "Oppfylt",
  "beregningsspor": "Alle tre delvilkår i sjekklisten er oppfylt => automatisk godkjent",
  "vilkarId": "<vilkarId>",
  "rettskildeIder": ["<rettskildeId>"]
}
POST /api/saker/{sakId}/vurderinger – delvurdering 
{
  "regelId": "<regelId>",
  "type": "Deterministisk",
  "utfall": "Oppfylt",
  "beregningsspor": "Innvendig fôring uten utvendig dimensjonsendring => rehabilitering",
  "vilkarId": "<vilkarId>",
  "forelderVurderingId": "<rotVurderingId>",
  "faktumIder": ["<faktumId>"]
}

For en Skjonn-vurdering legger du i tillegg ved hovedhensyn (påkrevd) og eventuelt forkastedeUtfall, begge som flerspråklige lister.

5. Partsmedvirkning (valgfritt)

Forhåndsvarsel, kommentarer og innsynskrav registreres med POST /api/saker/{sakId}/partsmedvirkning, og id-ene tas med i partsmedvirkningIder i neste steg.

6. Opprett vedtak

Vedtaket oppgir hvilke faktum, vurderinger og partsmedvirkninger som forklarer utfallet, pluss konkrete virkninger. Dette er øyeblikket alt fryses. Serveren setter tidspunkt og beregner automatiseringsGrad.

POST /api/saker/{sakId}/vedtak 
{
  "utfall": "Tillatelse til rehabilitering av skorstein innvilget",
  "faktumIder": ["<faktumId>"],
  "vurderingIder": ["<rotVurderingId>", "<delvurderingId>"],
  "partsmedvirkningIder": [],
  "virkninger": [
    {
      "type": "Tillatelse",
      "fastsettelsesmate": "Parametrisert",
      "vilkarId": "<vilkarId>",
      "varighet": "Varig",
      "beskrivelse": [
        { "spraakKode": "nb", "verdi": "Tillatelse til rehabilitering av skorstein" },
        { "spraakKode": "nn", "verdi": "Løyve til rehabilitering av skorstein" }
      ],
      "vurderingIder": ["<rotVurderingId>"],
      "faktumIder": ["<faktumId>"]
    }
  ]
}

Svaret (201) har vedtakId, tidspunkt, utfall og automatiseringsGrad. For virkninger med økonomisk innhold bruker du belop; for tidsbegrensede virkninger gyldigFra og gyldigTil; for plikter rapporteringsFrekvens og lopendeVilkar.

5

Samlet forklaring: ett kall

For å vise en sak komplett trenger du ikke sette den sammen av mange kall. To endepunkter gir alt i ett svar, og de svarer på to ulike spørsmål.

Se ekte svar: hele Sak A og hele Sak B (uten vedtak) fra GET /api/saker/{sakId}/forklaring, og vedtak-forklaringen for Sak A. Alle tre kan også leses og lastes ned på eksempelsiden.

Hvilket endepunkt skal jeg bruke?

Frosset øyeblikksbilde mot levende saksvisning

GET /api/vedtak/{id}/forklaringDet frosne øyeblikksbildet av ett vedtak: bare det forklaringsloggen peker på, pluss oppløste referanser.Du skal begrunne ett bestemt vedtak overfor en part, en klageinstans eller en revisor, og innholdet ikke skal endre seg.
GET /api/saker/{sakId}/forklaringHele saken levende: alt som finnes i saken nå, også det som ikke er frosset. Fungerer også uten vedtak, for eksempel for en sak rutet til manuell behandling.Du skal vise saken komplett i en saksbehandlerløsning, eller se status før et vedtak er fattet.

Begge gir 404 hvis saken eller vedtaket ikke finnes. I saksvisningen viser erLaast på hver rad hva som er frosset av et vedtak.

Flatt og nøstet er de samme radene

vurderinger og vurderingstre inneholder de samme vurderingene i to former: flatt for oppslag og filtrering, nøstet for å tegne hierarkiet uten å sette det sammen selv. Hver vurdering står dermed to ganger i svaret, og du skal ikke telle dem sammen.

Referansedata, refererte vurderinger og andre faktum

  • referansedata er katalograder svaret viser til, oppløst på stedet: kilder, rettskilder, regler og vilkår som er referert. Det inkluderer rettskildene som kilder, regler og vilkår selv peker på, og regelen et vilkår peker på.
  • refererteVurderinger er vurderinger i andre frosne saker som vurderingene her bygger på (regel 3.11). Bare ett nivå følges.
  • andreFaktum er faktum som er referert, men ikke oppført i forklaringsloggen, typisk fordi de tilhører en annen sak.

Avveining: størrelse

Svaret kan bli stort for store saker, og vurderingene finnes både flatt og nøstet. Trenger du bare en liten del, er de enkle listeendepunktene fortsatt billigere. Endringen er additiv: ingen databasemigrasjon, ingen brytende endring og ingen ny forretningsregel.

6

Konfigurasjon

Terskelen for når en KI-vurdering skal eskaleres er konfigurasjon, ikke en hardkodet konstant. I tillegg styrer en connection string hvilken database som brukes.

KonfidensTerskler

Seksjonen ligger i appsettings.json og bindes til KonfidensTerskelOptions:

{
  "KonfidensTerskler": {
    "Default": 0.7,
    "PerRegel": {
      "<regelId>": 0.85
    }
  }
}
  • Default er terskelen for alle regler som ikke har en egen verdi. Standardverdien er 0,7.
  • PerRegel er en ordbok der nøkkelen er regelId (GUID som tekst) og verdien er terskelen for akkurat den regelen. Den er tom som standard.
  • Som all ASP.NET Core-konfigurasjon kan verdiene overstyres med miljøvariabler, for eksempel KonfidensTerskler__Default=0.8.

Slik eskaleres en GenerativKI-vurdering

Når du registrerer en vurdering, slår VurderingService opp terskelen for vurderingens regelId (egen verdi i PerRegel, ellers Default). Så gjelder dette:

  • Er type GenerativKI og konfidens satt, og konfidens er lavere enn terskelen, settes eskalert til true av serveren. En konfidens lik terskelen eskalerer ikke.
  • Setter klienten selv eskalert: true, beholdes det. Serveren kan bare skru eskalering på, aldri av.
  • For andre vurderingstyper brukes terskelen ikke, og konfidens avvises med 400 hvis den er satt.
POST /api/saker/{sakId}/vurderinger – konfidens 0,62 mot terskel 0,7 
{
  "regelId": "<regelId>",
  "type": "GenerativKI",
  "utfall": "Oppfylt",
  "konfidens": 0.62,
  "beregningsspor": "Modellens tolkning av vedleggene"
}

Svaret har "eskalert": true, selv om klienten ikke sendte det.

Eskalering har konsekvens for vedtaket. automatiseringsGrad beregnes av serveren ut fra vurderingene som er listet i vurderingIder, der en vurdering teller som «ikke automatisk» hvis den er Skjonn eller eskalert:

Connection string

Databasen konfigureres under ConnectionStrings:Forklaringsmodell:

{
  "ConnectionStrings": {
    "Forklaringsmodell": "Data Source=forklaringsmodell.db"
  }
}

Mangler verdien, brukes den samme SQLite-adressen som reserve. Leverandøren er satt til SQLite i Program.cs. For en annen database må du bytte EF Core-leverandør og lage nye migrasjoner.

Kodeorganisering

Fire lag i src/ og et testprosjekt i tests/. Avhengighetene peker innover: Api og Infrastructure bruker Application, og Application bruker Domain.

Prosjektene i løsningen
ProsjektAnsvar
Forklaringsmodell.DomainEntiteter og enumer. Ingen avhengigheter til resten.
Forklaringsmodell.ApplicationDTO-er, FluentValidation-validatorer, use-case-services, unntakstyper, KonfidensTerskelOptions og repository-grensesnittet.
Forklaringsmodell.InfrastructureEF Core mot SQLite: DbContext, konfigurasjoner, migrasjoner, repository-implementasjon og seed-data.
Forklaringsmodell.ApiKontrollere, middleware som oversetter unntak til statuskoder, Swagger og Program.cs.
Forklaringsmodell.TestsxUnit: enhetstester av validatorer og services, og integrasjonstester mot hele API-et med WebApplicationFactory og en SQLite-database i minnet.

Kontrollerne er tynne: de kaller en service, som validerer manuelt, slår opp i repositoryet og kaster AppValidationException, NotFoundException eller AppendOnlyViolationException. Det er ExceptionHandlingMiddleware som gjør dem til 400, 404 og 409. Modellen bak endepunktene er beskrevet på Modell-siden og forretningsreglene på Regler-siden.
